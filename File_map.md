# File Map — Internal Audit App

This document lists all source files in the project, grouped by directory, with a brief description of each file's *current* purpose and role. This is a snapshot of what exists today — it does not track build history or phase status; see `CHANGELOG_ARCHIVE.md` for that.

---

## Root Directory

| File | Purpose |
|------|---------|
| `CLAUDE.md` | Project-level context for Claude Code: stack, architecture map, conventions, workflow rules, and a one-line-per-phase status log. Read automatically every session. |
| `CHANGELOG_ARCHIVE.md` | Detailed forensic write-ups of past phases (verification steps, test output) — only consulted when a phase touches an already-logged file/pattern. |
| `KNOWN_ISSUES.md` | Findings log for the Code Health Review protocol defined in `CLAUDE.md` — one row per finding (`Date \| Module \| Finding \| Severity`, severity being Fix / Feature / Defer). Append-only; kept out of `CLAUDE.md` because it grows on every review, same reasoning as `CHANGELOG_ARCHIVE.md`. Starts empty. |
| `CLINE.md` | Rules file for a separate AI tool, Cline (FIND/REPLACE code format, file-access/communication style) — not read by Claude Code. Appears to predate the current CLAUDE.md-driven workflow: it tells the agent to auto-determine affected files without asking, which conflicts with this project's current two-hard-stops rule in CLAUDE.md's Workflow rules. | `main.py` | FastAPI application entry point. Mounts `/static`, registers all 12 routers (dashboard, verification, import_export, templates, clients, data, error_log, settings, audit_rules, trial_balance, auth, users), and installs a global exception handler that logs unhandled errors to `error_log`. Runs Uvicorn when executed directly. |
| `requirements.txt` | Python dependencies: FastAPI, Uvicorn, Pandas, Pydantic, OpenPyXL, python-multipart, xlrd (legacy `.xls` reads for Trial Balance), bcrypt (password hashing for the new User module). |
| `run.bat` | Windows launcher — activates `venv` and starts Uvicorn on port 5000. |
| `.gitignore` | Keeps development-only artefacts out of version control: the SQLite database (`*.db`, plus its `-journal`/`-wal`/`-shm` sidecars), the automatic pre-migration backups `database.py` writes at runtime (`*.bak`, `*.db.bak*`), the `uploads/` folder of real client spreadsheets, Python bytecode/`venv/`, and uvicorn logs. Added 2026-08-08 after the tracked 23 MB `test.db` — rewritten in 308 of 423 commits — grew `.git` to 512 MB and started causing GitHub push timeouts. Does not shrink existing history; it only stops the growth. |
| `backfill_rate.py` | Standalone, manually-run script (Rate-derivation requirement, Phase 9 of 9, FINAL) — backfills a derived Rate value for historical Purchase Order/Store Receiving/Vendor Bill `client_data` rows that predate the Rate-derivation feature and still have Rate blank. Defaults to a dry-run report (counts per template: scanned/already-had-Rate/qty-zero-or-blank/no-Amount/would-backfill); `--run` performs the actual writes (`row_data`'s Rate + `rate_source='derived'`), reusing `get_rate_precision()`/`find_named_column()` from `routers/import_export.py` and mirroring `apply_rate_derivation()`'s derivation rule exactly. Not wired into any API endpoint. |
| `backfill_extract_amount.py` | Standalone, manually-run script (confirmed fix, 2026-08-09) — backfills `client_data.extract_amount` for every row where it's still NULL, using the fixed `extract_columns_from_row()` (`routers/import_export.py`). Unlike `backfill_rate.py`, deliberately scans ALL rows regardless of `is_deleted`/`change_detection_status` (a voucher line's FK target can be `is_deleted=1` after a later whole-dataset re-import, and still needs a correct `extract_amount`). Defaults to a dry-run report (counts per template: scanned/no-numeric-value-found/backfilled); `--run` performs the actual writes. Only ever writes `extract_amount`, never `extract_date`. Not wired into any API endpoint. |

| File | Purpose |

| `dashboard.py` | Root/health endpoints and the main dashboard's stats (total uploads, pending verifications, total records, last upload). |
| `data.py` | Client Data Bank backend: dataset listing, paginated row preview (`get_preview_rows` — search/amount/Sunday/data-quality filters, per-row voucher-line assignment flags, document grouping with subtotal rows), per-upload row listing, dataset/template soft-delete + restore, availability checklist, the per-day coverage calendar (`get_availability_calendar` — Sundays + firm-wide holidays), and the row revision history endpoint. |
| `error_log.py` | CRUD and stats for the `error_log` table populated by the global exception handler — list with filters, get one, mark resolved, delete, stats summary. |
| `import_export.py` | The upload/import flow: raw `.xlsx`/`.xls` upload, auto-mapping Excel headers to template columns, flexible date-format parsing (`parse_date_flexible`/`classify_date_cell`), row exclusion and force-include overrides, row-level rejection on blank Document ID/Amount/Date (`get_critical_field_columns`/`find_critical_blank_reasons`/`compute_data_quality_flag`), duplicate checking, validate-only, and the main validate+import endpoint with change detection (`compare_transactions` — groups by `document_group_id`, classifies unchanged/changed/new/missing). Also serves the downloadable template Excel and the Save Column Mapping feature (save/load/clear a client+template's column mapping). |
| `settings.py` | Get/update global app settings (date format, amount grouping, decimal precision, default date range, materiality threshold) stored as key-value pairs, plus full CRUD for the firm-wide Holiday list (`GET/POST /api/settings/holidays`, `PUT/DELETE /api/settings/holidays/{id}` — date/label/repeats-yearly, registered above the generic `/{key}` catch-all route). |
| `templates.py` | Master column CRUD (case-insensitive duplicate check, close-match advisory endpoint), template CRUD (with pivot-table column mappings, `sort_order`, quick-add-column support), template reordering, and backup/export + restore of the entire setup. Also hosts the Rate-derivation requirement's `rate_source` field (Phase 5 of 9) — `imported`/`derived`, restricted server-side (`resolve_rate_source()`) to the Purchase Order/Store Receiving/Vendor Bill templates only; any other template's `rate_source` always stores as NULL regardless of payload. |
| `verification.py` | Cash/Bank Verification module backend: per-client voucher-category detection (5-way scheme, `match_voucher_category`/`voucher_type_label`), cashbook/bankbook discovery, starting a verification session (voucher/line grouping via `document_group_id`), stepping through vouchers (`get_next_transaction`, `get_voucher_nav` — Prev/Next by whole voucher), saving/validating/completing lines, cashbook preview, the full audited-cashbook export, Audit Rules Category-based guidance lookup (`get_audit_guidance`, replacing the old hardcoded procedure library), the Voucher Supporting-Document Linking feature (assigning Data Bank rows to voucher lines as evidence, audit-procedure checklists, per-document observation capture/sync/roll-up into `verification_details.observations`), the Verification ↔ Assign Categories link (`category-for-account` lookup feeding the per-line Type field), the Validation Rules module's status engine/frontend endpoints (`compute_and_persist_cleared_status`, `voucher_approval`, `set_signature_exception`), the Account Head recommendation lookup (`suggest-account-head`, fuzzy-matches a line's description against the client's leaf Trial Balance accounts via `rapidfuzz`), and the Physical Bill evidence type's save/read endpoints (`save_physical_bill` upsert, `physical_bills/{voucher_line_id}` batch read via sibling-session resolution). |
| `auth.py` | Auth module backend (User module, all 7 phases done). `POST/GET /api/auth/login`/`logout` manage `sessions` rows against `users` (bcrypt password, HttpOnly cookie). `get_current_user(request)` validates the session cookie and returns the joined session+user row (now including `role`) — used as a route `Depends()` and called directly to gate pages. `require_admin` (Admin area, Phase 1 of 7) builds on it, 403s unless `role='admin'` — used by `routers/users.py`. `PUT /api/auth/select-client`/`GET /api/auth/current-client` read/write `sessions.selected_client_id`. |
| `users.py` | Manage Users backend (Admin area, Phase 2 of 7). CRUD over the `users` table, every endpoint behind `Depends(require_admin)`: list (`GET /api/users`, active-only by default), create (`POST`, bcrypt-hashes the password, rejects a duplicate username), edit username/role (`PUT /api/users/{id}`), soft-deactivate/reactivate (`POST .../deactivate`\|`reactivate`), and admin-set password reset (`PUT .../reset-password`). No self-deactivation/last-admin safeguard yet (deliberately deferred). |
| `audit_rules.py` | Audit Rules module backend: full CRUD (soft-delete/restore) for the three reusable rule-building entities — Documents (with auth roles, cross-check-eligible fields, and a `template_id` link to the Data Bank template their evidence is searched in), Cross-checks (comparison type + ordered list of Documents), and Categories (bundling Documents + Cross-checks, with a locked containment rule). Categories are what `verification.py`'s Transaction Type / audit guidance now sources from. Also hosts the Validation Rules module's backend (Phase 2 of 7): per-document `approval_required` toggle within a Category (`PUT /api/audit-rules/categories/{id}/documents/{doc_id}/approval`), automatic `matrix_version` bump (`bump_category_matrix_version()`, fired on document-membership change or an actual approval-flag change), and CRUD for `signature_specimens` (client+document+role → expected signatory name) — now soft-delete/restore like the other three entities (Soft-delete conversion, Phase 1 of 4 done): `is_active` column, `DELETE .../{id}` deactivates, `include_inactive` on the list GET, `POST .../{id}/restore`, plus a separate low-visibility `DELETE .../{id}/hard-delete` for genuine data-entry corrections only. Phase 2 of 4 done: the old DB-level `UNIQUE(client_id, document_id, role_name)` constraint is gone (table rebuild in `database.py`), replaced by app-level `validate_no_duplicate_active_signatory()` — blocks only a duplicate ACTIVE entry for the same person (name-matched); multiple different active people per role are allowed. |
| `trial_balance.py` | Trial Balance module backend. `POST /api/trial-balance/upload` reads a client's TB Excel file via an explicit column-mapping payload (8 standard fields: Code/Name/Opening Dr/Cr/Period Dr/Cr/Closing Dr/Cr, plus optional Type), classifies every account as parent/leaf from its code hierarchy, supports period-dated uploads with overwrite-conflict detection, and auto-carries forward Category assignments by account code. Also provides mapping suggestions, a downloadable standard template, per-upload account listing/summary/manual leaf-parent override, a list of all uploads for a client (Available Trial Balances), and the Category-assignment endpoints (`latest-accounts`/`assign-category`, smart-fill or force-apply cascade) that back the Assign Categories screen. |

## Notes

- **Static files** are served under `/static/` and rely on `client_context.js` for global client selection and navbar behavior on every page.
- **Routers** are mounted in `main.py`; each handles one domain (clients, verification, data, audit_rules, trial_balance, etc.).
- **Database** is SQLite; schema is fully managed by `init_db()` in `database.py`, including idempotent migration/upgrade blocks for tables that gained columns after going live.
- **Uploads** are stored in the `uploads/` directory (created at runtime).
- **Change detection** uses `document_group_id`/`change_detection_status` on `client_data`; document grouping everywhere in the app assumes the first template column (lowest `sort_order`) is a unique document key.
- **Voucher category detection** uses the 5-way `client_voucher_prefixes` scheme (Cash Payment/Cash Receipt/Bank Payment/Bank Receipt/Journal), storing Payment vs Receipt explicitly rather than deriving it from debit/credit sign.
