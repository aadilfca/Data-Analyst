## Conventions
- No inline event handlers (onclick, onload) in HTML
- No <script> inside HTML containers
- Meaningful comments on new/changed code
- In static/style.css, `.modal-content` and `.modal-header` are NOT shared base classes — each existing modal (#supportingModal, #procedureModal) defines its own `#<modalId> .modal-content` / `#<modalId> .modal-header` rules. When adding a new modal, add its own id-scoped rules rather than relying on `.modal-content`/`.modal-header` alone to style it.

- static/client_context.js's global navbar back-arrow (`.nav-back-arrow`) normally resolves its target statically per page (`<body data-nav-parent>` → `NAV_PARENT_MAP` → `index.html`, via `getBackTarget()`), rendered once at page load. For a single physical page with JS-driven in-page views (e.g. verification.html's `dashboardContent`/`cashbookContent`/`sessionContent`), where "back" means "the previous in-page view" rather than a fixed URL, use `window.setBackOverride(fn)` instead of trying to change `data-nav-parent` at runtime — it registers a function that a delegated click listener calls (with `preventDefault()`) instead of navigating; call `setBackOverride(null)` to restore the static default when back at the page's entry view. See verification.js's `startSessionFromCashbook()`/`exitSession()` for the reference implementation (reuses `exitSession()` itself as the override, no new transition logic).
- `client_voucher_prefixes` (database.py) uses a 5-way category scheme — `Cash Payment`/`Cash Receipt`/`Bank Payment`/`Bank Receipt`/`Journal` (see `VOUCHER_PREFIX_CATEGORIES`/`DEFAULT_VOUCHER_PREFIXES`) — that stores Payment vs Receipt explicitly per prefix, rather than deriving it from debit/credit sign at detection time. This replaced an earlier 3-way `Cash`/`Bank`/`Journal` scheme that had no way to tell Payment from Receipt before a cashbook name was already known, which was the root cause of a real bug (`extract_cashbook_name()` in routers/verification.py briefly accepted either debit or credit as a cashbook candidate, surfacing expense/vendor accounts as false cashbooks). `match_voucher_category()` (routers/verification.py) now returns one of the 5 category names directly, and `voucher_type_label(category)` maps it straight to CPV/CRV/BPV/BRV/JV with no `is_credit_side` parameter — do not reintroduce debit/credit-sign-based Payment/Receipt derivation anywhere in verification.py; the category already carries that information. `routers/clients.py`'s `VoucherPrefixesUpdate`/`CATEGORY_FIELD_MAP` bridge between the 5 category display names (which contain spaces, e.g. `"Cash Payment"`, used as dict keys everywhere) and Python-identifier-safe Pydantic field names (`cash_payment`, etc., used only in the PUT request body) — `static/client_settings.js`'s `CATEGORIES` array mirrors this with `{key, field, id}` objects. `create_client()` (routers/clients.py) now seeds every new client with the 5 defaults (CPV/CRV/BPV/BRV/JV) at creation time via `save_client_voucher_prefixes()` — previously a new client had zero prefixes configured until manually set up via Client Settings. Pre-existing databases with old-scheme rows are migrated automatically and idempotently in `init_db()` (database.py) — SQLite can't ALTER a CHECK constraint, so this does a rename→recreate→copy→drop table rebuild, remapping each old `Cash`/`Bank` row via a letter heuristic (`'R' in prefix → *_Receipt, else → *_Payment`, matching the original pre-per-client hardcoded CPV/CV-vs-CRV/CR bucketing) and taking a timestamped `test.db.bak-premigrate-<timestamp>` file backup first; only runs when old-scheme rows are actually detected, so it's a no-op on every subsequent startup.
