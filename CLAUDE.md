## Conventions
- No inline event handlers (onclick, onload) in HTML
- No <script> inside HTML containers
- Meaningful comments on new/changed code
- In static/style.css, `.modal-content` and `.modal-header` are NOT shared base classes — each existing modal (#supportingModal, #procedureModal) defines its own `#<modalId> .modal-content` / `#<modalId> .modal-header` rules. When adding a new modal, add its own id-scoped rules rather than relying on `.modal-content`/`.modal-header` alone to style it.
- Keep changes scoped — don't touch unrelated code
- Document grouping (get_document_group_id in routers/import_export.py) assumes the first template column (lowest sort_order) is a unique document key. Do not reorder template columns without checking this assumption holds.
- static/verification.js: `renderTransaction()` (the old standalone single-transaction card) is long deleted. `#transactionCard` itself no longer exists in the DOM (removed entirely, not just inert). Everything lives per-line in `#voucherLinesContainer`/`renderVoucherLines()`. Session-header chrome is split by scope: Prev voucher, the voucher title (with the 🔍 view-all icon inline right next to the voucher number — that's how you search for a specific voucher, so it's a sibling of the voucher number, not a toolbar action) + subtitle, and Next voucher live in `#voucherHeaderBar`, **inside** `.voucher-panel` so this row aligns flush with the table's 60% width; Cashbook return is a page-level action and lives separately in `#cashbookBar`, **outside** `.voucher-panel`, pinned to the extreme right of the full page. Both are rendered together by `renderVoucherHeader()` (Cashbook via a second `innerHTML` write into `#cashbookBar` in the same function) and cleared together by `clearVoucherHeader()`, re-rendered on every voucher load/nav. (Earlier phases briefly tried a full-width single row and a separate `#verificationToolbar` — both reverted per direct user feedback; check with the user before changing this split again.) There is no Save Progress button anywhere — confirmed redundant, autosave already covers Prev/Next/Complete/Exit. Each line's expanded panel (`buildLineDetailHtml()`) is now just one `.expanded-bar` row: Audit Guidance + Supporting buttons (left group, `.expanded-bar-actions`) and the transaction-type dropdown (right group, `.expanded-bar-type`) — no Particulars/Value table, no DFD/AUDIT tabs, no Observations/Comments fields on this page anymore (all deliberately removed, not just relocated — confirm with the user before re-adding any of them). Watch for unscoped `document.querySelectorAll('.classname')` when adding new elements — the earlier `renderTransaction()` bug (prior Phase 3 note) is the failure mode to avoid.
- static/verification.js/style.css: the voucher line summary row (`renderVoucherLines()`) is a CSS grid with columns Account Code / Account Name+desc / Amount / Status / chevron (`.voucher-line-summary-grid`, shared with the column-title row and the total row so all three line up — cells get `min-width: 0` since flex/grid children default to content-based min-width, which previously let long description text overflow past its column). Amount is a single plain number (`getVoucherLineAmount()`, `.voucher-line-amount`) — this cashbook only ever populates one side per voucher type (Debit for CPVs, Credit for CRVs; the other is always zero at source), so there is no Dr/Cr distinction anywhere in this view, and no "Dr"/"Cr" text prefix. There is no transaction-type badge in the summary row (type only shows/edits via the dropdown inside the expanded panel) — validation status color/icon lives on `.voucher-line-status` (`data-validation-status` attribute), which is what `validateTransaction()`/`goToNextTransaction()` write to. The table is a continuous "All Borders" grid (header row / line rows / total row all share cell borders via `.voucher-line-summary-grid > *`), not individual per-row boxes — the header and total rows share the same dim-blue (`#dbeafe`) background as a matched pair around the white body rows.
- Text colors in the voucher table follow the app's established primary/secondary/muted trio (`#1a1a2e` / `#64748b` / `#94a3b8`, used pervasively elsewhere in style.css) — don't introduce new one-off hex values for body text there (e.g. `#666`); status colors (pending/passed/failed) are the semantic exception and are intentionally distinct.
