Also returns `rate_source` per row, read straight from `client_data.rate_source`, consumed by `static/databank.js`'s `renderPreviewRows()` to show a 📥/🧮 provenance icon on a non-blank Rate cell — see "Rate-Derivation Requirement" in CHANGELOG_ARCHIVE.md for the full design/build history.

Also hosts the Save Column Mapping feature's backend: `saved_column_mappings` table (database.py) + `POST/GET /api/upload/save-mapping`/`/api/upload/saved-mapping`, keyed by client_id+template_id — see "Save Column Mapping" in CHANGELOG_ARCHIVE.md. Also hosts Rate derivation at import time: `get_rate_precision()` (reads the `rate_precision` app_settings key), `find_named_column()` (case-insensitive/trimmed column_name lookup), and `apply_rate_derivation(row_data, template_cols, rate_source, rate_precision)` — for Purchase Order/Store Receiving/Vendor Bill templates only, computes `row_data['Rate']` as Amount ÷ Quantity when `rate_source='derived'` (Quantity missing/blank/0 leaves Rate as `None`, never an error) or rounds an already-imported Rate column when `rate_source='imported'`, both rounded to `rate_precision`. Called in `compare_transactions()`'s incoming-row loop and `validate_and_import()`'s first-time-upload branch — **must stay before change-detection's diff runs**, or every re-upload of an already-imported row looks artificially "changed" (a stored row already carries a Rate value; a freshly-rebuilt comparison row without one injected first would never match). `validate_only()` is deliberately untouched. `reorder_row_data_by_template()` runs right after both call sites to keep `row_data`'s stored key order matching the template's `sort_order`. `client_data.rate_source TEXT` (nullable) is the per-row audit trail of how that row's Rate was actually obtained, set at all 3 write points from the already-resolved `rate_source` variable, recorded even when Rate itself is null. `extract_columns_from_row()`'s amount/date extraction uses independent found-flags (not a shared `break`) and prefers a column literally named "Amount" over "first Numeric column" — see "Rate-Derivation Requirement" in CHANGELOG_ARCHIVE.md for the full design, the historical `extract_amount`-was-always-NULL bug, and both one-time backfill scripts (`backfill_rate.py`, `backfill_extract_amount.py`).

Also hosts the firm-wide Holiday list feature: `database.py`'s `holidays` table + `GET/POST /api/settings/holidays`, `PUT/DELETE /api/settings/holidays/{id}`, with add/view/delete UI in `static/settings.html`/`.js` — see the Conventions note below and "Client Data Availability & Coverage Redesign" in CHANGELOG_ARCHIVE.md.

## Conventions
- No inline event handlers (onclick, onload, onchange, etc.) in HTML
- No <script> inside HTML containers
- Meaningful comments on new/changed code
- No "temporary code" shortcuts — proper separation of concerns; if something genuinely needs a stopgap, flag it explicitly rather than leaving it disguised as a normal implementation
- In static/style.css, `.modal-content` and `.modal-header` are NOT shared base classes — each existing modal (#supportingModal, #procedureModal) defines its own `#<modalId> .modal-content` / `#<modalId> .modal-header` rules. When adding a new modal, add its own id-scoped rules rather than relying on `.modal-content`/`.modal-header` alone to style it.
- Keep changes scoped — don't touch unrelated code
- static/client_context.js's global navbar back-arrow (`.nav-back-arrow`) normally resolves its target statically per page (`<body data-nav-parent>` → `NAV_PARENT_MAP` → `index.html`, via `getBackTarget()`), rendered once at page load. For a single physical page with JS-driven in-page views (e.g. verification.html's `dashboardContent`/`cashbookContent`/`sessionContent`), where "back" means "the previous in-page view" rather than a fixed URL, use `window.setBackOverride(fn)` instead of trying to change `data-nav-parent` at runtime — it registers a function that a delegated click listener calls (with `preventDefault()`) instead of navigating; call `setBackOverride(null)` to restore the static default when back at the page's entry view. See verification.js's `startSessionFromCashbook()`/`exitSession()` for the reference implementation (reuses `exitSession()` itself as the override, no new transition logic).
- `client_voucher_prefixes` (database.py) uses a 5-way category scheme — `Cash Payment`/`Cash Receipt`/`Bank Payment`/`Bank Receipt`/`Journal` (see `VOUCHER_PREFIX_CATEGORIES`/`DEFAULT_VOUCHER_PREFIXES`) — storing Payment vs Receipt explicitly per prefix, not derived from debit/credit sign. `match_voucher_category()`/`voucher_type_label()` (routers/verification.py) return/consume the category directly — do not reintroduce debit/credit-sign-based Payment/Receipt derivation anywhere in verification.py. `routers/clients.py`'s `CATEGORY_FIELD_MAP` bridges the 5 category display names to Pydantic-safe field names (`static/client_settings.js`'s `CATEGORIES` array mirrors this); `create_client()` seeds every new client with the 5 defaults. See "Bank Verification Project" in CHANGELOG_ARCHIVE.md for the full migration/bug-history design.
- Document grouping (get_document_group_id in routers/import_export.py) assumes the first template column (lowest sort_order) is a unique document key. Do not reorder template columns without checking this assumption holds.
- `parse_date_flexible(value, delimiter, order)` in routers/import_export.py is the single source of truth for date-import parsing (text-string dates), used by validate_only(), validate_and_import(), and extract_columns_from_row() — do not reintroduce a hardcoded `datetime.strptime(value, "%d/%m/%Y")` or a per-function format list; extend/call this function instead. Paired with `classify_date_cell(value)` (same file), which classifies a raw cell as `'native'` (must NOT be passed to `parse_date_flexible()`), `'text'`, `'excel_serial'`, or `'empty'` — all three Date call sites dispatch on this classification rather than inline `isinstance()` checks. See "Flexible Date-Import Format" in CHANGELOG_ARCHIVE.md for the full phase-by-phase design.
- `json_safe_cell_value(value, date_fmt)` in routers/import_export.py is the single source of truth for coercing a raw pandas/openpyxl cell into something safe for a row_data dict/`json.dumps()` — used by `count_new_and_existing_rows()`, `compare_transactions()`, `validate_only()`, and `validate_and_import()`. Do not reintroduce the old inline `if pd.isna(value): value = None` / `if isinstance(value, datetime): value = value.strftime(...)` pattern elsewhere — it missed a bare `datetime.time` value, which crashed `json.dumps()` in production. **Known remaining gap**: `check_duplicates()` (same file) still has the old unfixed inline pattern. See "Upload Reliability & Blank-Field Handling" in CHANGELOG_ARCHIVE.md for the full incident writeup.

- `filter_excluded_rows(rows, excluded_rows)` in routers/import_export.py is the single point where session-only row exclusion is applied — called immediately after `rows = df.to_dict('records')` in both `validate_only()` and `validate_and_import()`, before any validation, counting, or `compare_transactions()`/`get_document_group_id()` grouping sees the rows. `excluded_rows` (on `ImportRequest`) uses the same Excel row-number scheme as `validation_errors[].row_number` (header=1, first data row=2). - `extract_columns_from_row(row_data, template_cols, ...)` in routers/import_export.py — three non-obvious rules, all confirmed live (2026-08-09), do not regress them: (1) amount/date are found via **independent** found-flags, never a shared `break` — a shared break previously let the loop exit the moment it found EITHER, and since every template lists its Date column before its Amount column, `extract_amount` came out NULL on every real row for years. (2) A literal `0` in a Numeric column is treated as "no value here," not a valid found amount — the Transaction Report (cashbook) template always stores both Debit Amount and Credit Amount as real numbers, never blank, so without this a Debit-side `0` on a receipt-type voucher would permanently win over the real Credit Amount (matches `is_cashbook_leg_row()`'s own 0-means-"not this side" convention). (3) A column literally named "Amount" (via `find_named_column()`) is preferred over the generic "first Numeric column" rule — Purchase Order/Store Receiving/Vendor Bill all have Quantity (also Numeric) before Amount in `sort_order`, and `GET /api/data/preview`'s `amount_min`/`amount_max` filter reads `extract_amount` directly, so "first numeric" would silently resolve to Quantity there. See `backfill_extract_amount.py` for the one-time backfill this fix required.

A JS-stamped class (e.g. `group-start`) survives that kind of change.
