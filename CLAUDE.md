- No <script> inside HTML containers
- Meaningful comments on new/changed code
- Any new module or in-module feature must register itself in `NAV_MANIFEST` (`static/client_context.js`) — including a `children` entry with `keywords` if it should be searchable. This is the single source of truth for both the ⊞ quick-nav dropdown and the search field; a feature left out of it is undiscoverable through either.

- **A page script must `await window.clientContextReady` before reading the selected client — never assume `window.onload` outruns the session fetch.** `initClientContext()` is `async` and awaits `loadSessionClient()`, a real network call started at `DOMContentLoaded`; `window.onload` waits on subresources, which says nothing about an in-flight `fetch()`. On a light page (scripts at end of body, no images) `onload` fires first, so a synchronous `getSelectedClientId()` there returns `null` and the page wrongly renders its "no client selected" state — proven live 2026-08-22 (`null` at the load event, correct id after the signal, on all three pages tested). `window.clientContextReady` (static/client_context.js, created at parse time, resolved at the end of `initClientContext()` once both the cache and navbar are ready) is the fix; it resolves on a valid session and never rejects, but is deliberately left permanently unresolved on a 401 (session expired/invalid) — the page is already navigating to login.html in that case, and resolving it would wake page scripts mid-navigation with a null client cache (see the session-expiry fix in the Status log). Pattern: `window.onload = async function () { if (window.clientContextReady) await window.clientContextReady; ... }`. Applied to `trial_balance.js`/`databank.js`/`verification.js`; `upload.js`/`audit_rules.js`/`template-viewer.js` still have the race (logged in `KNOWN_ISSUES.md`). Do not "fix" a symptom of this with a `setTimeout` delay.
- **A live tile on Verification's own hub is declared by `data-verification-type` on the tile, not by a handler of its own.** One delegated listener on `#dashboardContent` (static/verification.js) picks up every tile carrying it, locks it on click (spinner via `LoadingUI` + the `hubTileNavigationInFlight` guard) and navigates to `?type=<that value>`. **Add the attribute to make a new tile live — do not add a per-tile `addEventListener`**, or that tile silently skips the spinner and the double-click lock. A "Coming soon" tile omits it and stays inert. The lock must be the JS flag, not `disabled`: a `.module-card` is a `<div>`, so `showSpinner`'s `isButton` test is false and it never sets `disabled` — there is no native disabled state here. The same page also locks the matching tile at **script-parse time** on arrival, gated on the *identical* condition `window.onload` uses to decide it will open the popup — `setVerificationUrl()` writes `state` and `type` together, so a `?state=session&id=N&type=cash` restore URL carries a `type` yet never opens the popup, and a looser "is `?type=` present" check would strand a spinner there permanently. Three release paths, all real events rather than guessed durations: the `finally` around `window.onload`'s popup-open region, `pageshow` with `event.persisted` (bfcache Back-restore), and `keydown` Escape (the browser's own Stop-loading gesture, the one case where a cancelled navigation leaves the old document alive with a locked tile). ### Data & Performance Engineering Standard
 - **Prepare once, report fast, verify always:** interns/processors classify categories, Cash/Bank, and derived periods during controlled upload preparation—the practical “desi” preparation layer—while executives receive fast reports from validated read models.
 - Keep raw source rows unchanged; prepared results and browser caches are never the accounting source. Scope read models by client, uploads, configuration, and revision, with canonical SQL fallback when preparation is missing or stale.
 - Prefer one compact server request, server-side filtering/pagination, bounded payloads, indexed queries, bulk operations, and limited retries for safe reads; keep each Treasury view, period grain, and grouping configuration explicit.
 - Key caches by complete report context and revision; invalidate after source or configuration changes, abort obsolete requests, reject stale responses, and preserve a hard-refresh path when freshness is uncertain.
 - Design for slow or intermittent Sialkot connectivity: show progress, use bounded timeouts/retries, preserve usable UI, and avoid blocking alerts.
 - Test cold and warm loads, parent/child period reuse, changed backend data, delayed/failed requests, empty and large periods, reconciliation totals, export parity, and multi-user freshness before release.
 - Add every future proven data, database, fetching, caching, performance, or integrity technique here and follow it in every later development.
