## Conventions
- No inline event handlers (onclick, onload) in HTML
- No <script> inside HTML containers
- Meaningful comments on new/changed code
- In static/style.css, `.modal-content` and `.modal-header` are NOT shared base classes — each existing modal (#supportingModal, #procedureModal) defines its own `#<modalId> .modal-content` / `#<modalId> .modal-header` rules. When adding a new modal, add its own id-scoped rules rather than relying on `.modal-content`/`.modal-header` alone to style it.
- Keep changes scoped — don't touch unrelated code
- static/client_context.js's global navbar back-arrow (`.nav-back-arrow`) normally resolves its target statically per page (`<body data-nav-parent>` → `NAV_PARENT_MAP` → `index.html`, via `getBackTarget()`), rendered once at page load. For a single physical page with JS-driven in-page views (e.g. verification.html's `dashboardContent`/`cashbookContent`/`sessionContent`), where "back" means "the previous in-page view" rather than a fixed URL, use `window.setBackOverride(fn)` instead of trying to change `data-nav-parent` at runtime — it registers a function that a delegated click listener calls (with `preventDefault()`) instead of navigating; call `setBackOverride(null)` to restore the static default when back at the page's entry view. See verification.js's `startSessionFromCashbook()`/`exitSession()` for the reference implementation (reuses `exitSession()` itself as the override, no new transition logic).
- Document grouping (get_document_group_id in routers/import_export.py) assumes the first template column (lowest sort_order) is a unique document key. Do not reorder template columns without checking this assumption holds.
- `parse_date_flexible(value, delimiter, order)` in routers/import_export.py is the single source of truth for date-import parsing (text-string dates), used by validate_only(), validate_and_import(), and extract_columns_from_row(). Do not reintroduce a hardcoded `datetime.strptime(value, "%d/%m/%Y")` or a per-function format list in this file — extend/call this function instead. Defaults (`DEFAULT_DATE_DELIMITER`/`DEFAULT_DATE_ORDER`, both DD/MM/YYYY) are now only a fallback for when `ImportRequest.date_delimiter`/`date_order` are absent — as of Phase 4 the Upload page's Date Delimiter/Date Order dropdowns (static/upload.js `selectedDateDelimiter`/`selectedDateOrder`) are sent on every validate/import call and resolved per-request as `effective_delimiter`/`effective_order` at the top of `validate_only()`/`validate_and_import()`, then threaded through to `parse_date_flexible()` and `extract_columns_from_row()` (which also takes optional `delimiter`/`order` params now, still defaulting to the module constants for any other caller). Paired with `classify_date_cell(value)` (same file, same section), which classifies a raw cell as `'native'` (real Excel date, e.g. datetime/Timestamp — must NOT be passed to `parse_date_flexible()`), `'text'` (needs `parse_date_flexible()`), `'excel_serial'` (bare int/float, handled by its own serial-to-date conversion), or `'empty'`. All three Date call sites dispatch on this classification rather than inline `isinstance()` checks — extend `classify_date_cell()`'s categories instead of adding new ad hoc type checks elsewhere in the file.

- **Known pre-existing bug, not yet fixed (found 2026-07-16 while verifying the row-exclusion phase)**: `compare_transactions()`'s existing-rows query (`routers/import_export.py`) does a `LEFT JOIN verification_details` that can return multiple rows per `client_data_id` when more than one `verification_details` row references the same `client_data_id` — this inflates `existing_docs`/the "missing" list with duplicate `client_data_id`s (harmless duplication on its own, since re-`UPDATE`ing the same id is idempotent) but also means `total_existing_before_import`/`missing_count` in API responses can overcount real rows. Caught the hard way: testing `/api/upload/import` against the *real* ACME client (client_id=1) with a small unrelated test file caused every real document not present in that test file to be correctly-by-design-but-dangerously flagged `change_detection_status='deleted'` (~1200 rows momentarily mis-flagged; reverted using `data_audit_log` history to confirm each row's true prior status, no data loss). **Lesson for future testing**: never call `/api/upload/import` (or anything that reaches `compare_transactions()`) against a client that has real/live data unless the incoming file is a genuine full re-upload of that client's data — use a disposable test client (create via `POST /api/clients`, delete afterward) for any import-path testing instead.
- Row selection grid (Phase 2 of the row-exclusion requirement, static/upload.html + static/upload.js) state: `excludedRowNumbers` (a `Set` of Excel row numbers the user unchecked — same scheme as `validation_errors[].row_number`/backend `excluded_rows`: header=1, first data row=2), `rowExclusionAllRows`/`rowExclusionHeaders` (current sheet's raw rows/headers, read via `XLSX.read(workbookData, ...)` the same way `showPreview()` does), `rowExclusionCurrentPage`, and the fixed `ROW_EXCLUSION_PAGE_SIZE = 10`. `renderRowExclusionGrid()` (rebuild from scratch, resets `excludedRowNumbers` to empty) is called once per successful `autoMapColumns()`, right after `refreshDateFormatPreview()`. `renderRowExclusionPage()` renders one page and must stay the only place that reads/writes `excludedRowNumbers` per-row, so future phases (auto-flag heuristic, counter, Select All/Deselect All, reset-on-change) extend this same Set/functions rather than introducing a second numbering or state scheme. - Phase 4 (final) additions to the row selection grid (same files, `routers/import_export.py` untouched — purely frontend): `validationFailedRows` is a `Map<excelRowNumber, errorsArray>` (the `errors` field from a `validate`/`import` response's `errors[]`, same `{column, excel_column, error_type, message}` shape `showValidationErrors()` renders) — kept deliberately separate from `excludedRowNumbers`, since a validation failure must never auto-exclude a row (it stays checked/included by default). `setValidationFailedRows(errorsList)` rebuilds the Map and re-renders the current page if the grid is visible; called from all three places a validate/import response can report row errors: the `importBtn` click handler's `has_errors: true` branch, its `has_errors: false` branch (clears stale markers from an earlier failed attempt), and `performImport()`'s `status === 'validation_failed'` branch. `resetRowExclusionSelections()` is the lighter reset for a per-column remap in the mapping table (`renderMapping()`'s `select` `change` listener) — unlike a sheet change, the underlying rows haven't changed, so it just clears `excludedRowNumbers`/`validationFailedRows` and re-renders (flags recompute fresh from `currentMappings[0]` automatically); a full sheet/file change still goes through `renderRowExclusionGrid()` (which now also clears `validationFailedRows`, alongside its existing `excludedRowNumbers` reset), and `resetUpload()` clears `validationFailedRows` too. - Any `XLSX.utils.sheet_to_json(sheet, { header: 1 })` call in `static/upload.js` whose row arrays feed a `.forEach()`-based renderer must pass `defval: ''`. Without it, a genuinely blank Excel cell leaves a hole in the row array (not an explicit empty value); `Array.prototype.forEach()` silently skips holes, so no cell gets rendered for that column and every later value in the row shifts one column to the left. `getFirstDataRow()` (Mini Preview) is the one exception — it reads cells by direct index (`row[idx]`), which tolerates holes correctly, so it doesn't need `defval`.
